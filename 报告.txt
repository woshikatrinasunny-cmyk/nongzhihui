第三章 产品介绍
3.1产品定位
“农智汇·开源涉农知识聚合平台”是聚焦乡村振兴需求、面向农户和基层农技人员的智能涉农知识聚合搜索引擎与方言智能问答平台，包括网页端和小程序端，由两大功能引擎驱动：涉农知识聚合搜索引擎通过实时聚合百度、Bing等主流搜索引擎的涉农资源，结合领域定向查询改写技术，实现对农业农村部政策库、全国人大法律库、各省农业厅技术文档等资源的一键跨库检索；耒阳方言农业智能问答系统以Qwen2-7B大语言模型为基座，经方言语料和涉农政策数据的指令微调，能够理解和使用耒阳方言进行自然语言交互。搜索引擎解决涉农信息“找不着”的问题，智能问答解决“看不懂”和“不会办”的问题。
3.2 系统架构
平台采用五层架构：顶层为微信小程序和Web双端入口，经API网关层统一接入后，由业务逻辑层调度搜索聚合、智能问答等核心服务，底层分设数据采集与聚合层（多源爬虫+本地知识库）和大语言模型层（Qwen2-7B +方言语义映射），分别处理搜索请求和问答请求。

（2）耒阳方言语料采集
方言语料的采集是智能问答系统方言能力的基础。团队通过三种途径构建耒阳方言语料库：从耒阳本地论坛、社交媒体和方言研究文献中收集方言词汇和例句；通过实地访谈录制耒阳本地农民的日常对话，经人工转写和标注形成对话语料；参考《耒阳方言研究》（王箕裘、钟隆林）、《湖南方言调查报告》、《耒阳县志》等文献资料，整理方言词汇的标准释义和使用语境。
最终构建的方言语料库包含方言词条约1,200条，按14个语义类别组织，涵盖天文、地理、时令节气、农事操作、植物作物、动物家畜、农具器械、饮食加工、房屋建筑、服饰穿戴、人体疾病、亲属称谓、日常用语和农谚俗语。
每条词条按六字段结构标注：方言词条、普通话通用释义、词性标注、使用语境标签集合、情感极性标注、涉农领域语义字段。其中涉农领域语义字段用于记录方言词条在农业语境下的特殊含义，同一方言词条允许存在多条记录对应不同语境下的不同释义，形成歧义候选集，为后续的上下文歧义消解提供数据支撑。下表展示了完整的六字段标注结构。

3.4.2 模型基座选择
智能问答系统的核心是大语言模型的选型。团队首先对农业领域大语言模型的研究现状进行了系统调研。当前，农业领域LLM评测已形成若干具有代表性的学术基准：AgriEval基准（哈尔滨工业大学，2024）包含14,697道选择题和2,167道开放问答题，覆盖作物科学、畜牧兽医、农业经济等子领域，对51个主流LLM的测试显示大多数模型在农业领域的准确率低于60%；AgXQA基准聚焦农业问答任务，当前最优模型的精确匹配分数为55.15%，F1分数为78.89%。上述基准表明，通用模型难以直接满足农业领域需求，领域微调是提升
性能的必要手段。

（4）模型选择依据
综合客观评测和主观评测结果，Qwen2-7B 在涉农知识理解、方言处理和文本生成三个关键维度上均展现出相对优势。从工程部署角度，Qwen2-7B 参数规模适中，可在 NVIDIARTX 3090（24GB）上完成全精度推理，在 RTX 4060（8GB）上可通过 4-bit 量化推理；阿里云提供 DashScope API 服务支持按量付费调用，降低了自建推理服务的运维负担；模型采用 Apache 2.0 开源协议，支持商业应用和二次开发。基于上述分析，团队选择 Qwen2-7B作为基座模型，通过 DashScope API 调用其指令微调版本 qwen-turbo 进行在线服务。

3.4.4 对话管理与提示工程
智能问答系统的对话处理链路如下图所示，从用户输入到回答生成经历六个核心环节。

图28 智能问答处理流程
各环节的核心技术实现如下：
方言语义识别与歧义消解。用户输入经分词后遍历方言-普通话双向语义映射词典进行匹配。命中唯一词条时直接替换为普通话释义，若当前上下文属于涉农语境且涉农领域语义字段非空则优先使用涉农释义。命中多个歧义候选时，提取前后各 2 至 5 个词作为局部上下文窗口，计算语境标签匹配度选择最优候选。当匹配度低于消歧置信度阈值（0.5–0.7）时优先选择涉农语义非空的候选。测试集评估显示歧义消解在涉农语境下准确率为 82.4%。
意图识别与槽位填充。对标准语义表示执行意图分类和槽位填充的联合处理。意图分类采用规则引擎与预训练语言模型分类器相结合，定义政策咨询、技术指导、补贴查询、经营管理四个类别，测试集宏平均 F1 为 87.3%。槽位分为基础槽位和根据意图类别动态加载的专属槽位，多个必要槽位缺失时按优先级逐一澄清。领域知识检索与冲突检测。政策知识库按时间维度进行三级分层（当前年度/前一年度/更早），各层分配不同检索权重。检索后通过语义向量余弦相似度进行相关性重排序，并执行两级冲突检测：显性冲突（废止/修订关系）和隐性冲突（地域包含关系下的取值差异）。
结构化提示组装。将方言词典子集、政策条目、对话状态和对话历史组装为四区段结构化提示模板：角色定义、方言能力、领域知识、回答约束。根据意图类别动态调整采样温度（政策类 0.3，技术类 0.7）。
多轮对话状态管理。为每个会话维护对话状态，对话历史采用基于话题的动态窗口机制（上限8–12轮），意图变化时将前一话题压缩为摘要存入长期记忆。支持人称代词、指示代词、零代词和名词短语指代四种类型的指代消解，整体准确率 79.6%。
3.4.5 搜索引擎聚合实现
核心技术环节包括：查询改写（域名限定注入和领域术语扩展）、多源并发（每引擎 8秒超时，竞速机制先返回先处理）、熔断降级（连续 3 次失败标记不可用，5分钟后恢复探测）、结果解析清洗（专用 HTML 解析器，主备双规则）、智能分类与三级权威评级（官方/专业/一般）、两层去重（URL 精确比对 + 标题哈希比对）、四种排序模式（综合/时间/权威/热度）、LRU 缓存（热门查询缓存 30 分钟，命中时响应从 3.2 秒降至 50 毫秒）。
3.4.6 系统部署与运维
后端基于 Node.js 18 LTS + Express 4.x构建RESTful API，Web前端基于Flask +Jinja2，微信小程序采用原生框架（AppID: wxfa75e9bfc254e34d），三端共享同一后端 API。代码托管在GitHub，配置CI/CD自动部署流水线。后端地址https://nongzhihui-api.onrender.com，Web前端地址 https://nongzhihui-web.onrender.com。针对云平台资源限制（512MB 内存、无持久化存储），搜索聚合采用实时抓取而非预存储模式，对话历史和缓存使用内存存储并控制上限，本地知识库以 JSON文件随代码部署。针对冷启动问题实现每14分钟定时心跳保活。系统实现三级降级：后端不可用时小程序切换本地知识库；单个搜索引擎不可用时使用其他引擎结果；大语言模型 API 不可用时降级为关键词匹配问答。API 密钥通过环境变量注入，通信全程 HTTPS 加密，用户数据均存储在设备本地不上传服务器。
